# 测试与验证策略

> **文档定位**：本文规定本项目如何选择测试层级、何时运行全量测试、如何使用真实
> 外部依赖以及如何报告验证证据。
>
> **权威顺序**：用户明确指令和 `AGENTS.md` 优先；BMAD 产物决定项目阶段、范围和
> 任务顺序；`PROJECT.md` 与版本规格决定质量目标和验收契约；本文只规定验证方法和
> 执行门禁。

## 1. 目标

测试必须同时满足以下目标：

1. 发现当前变更引入的回归。
2. 为当前任务提供与风险相称的验证证据。
3. 保持默认离线、可重复、低成本和可并发执行。
4. 避免每次修改都运行全量测试、重复输出相同结果或隐式消耗付费额度。

测试成本包括执行时间、上下文和输出 Token、外部 API 费用、网络不稳定性和数据
风险。成本降低不能以跳过与变更风险直接相关的验证为代价。

## 2. 测试层级

| 层级 | 目的 | 典型范围 | 默认时机 |
| --- | --- | --- | --- |
| 单元测试 | 验证纯函数、领域规则和局部状态 | 目标模块及直接依赖 | 每次相关修改 |
| 集成测试 | 验证组件、数据库、API 和事务边界 | 目标模块及相邻调用链 | 每次相关修改或模块验收 |
| 契约/API 测试 | 验证请求、响应、错误码和兼容性 | OpenAPI、Schema、调用方契约 | 接口变更时 |
| E2E 测试 | 验证完整用户链路 | 抓取至证据返回等主路径 | 阶段验收或高风险变更 |
| 质量评测 | 验证解析、检索、双语和引用质量 | 冻结语料、基线、指标 | 质量相关变更和阶段验收 |
| 真实依赖检查 | 验证当前外部环境仍可用 | 公开网页、真实 API、真实数据库副本 | 显式授权后独立执行 |
| 全量测试 | 发现跨模块回归 | 项目全部自动测试 | 本文第 4 节触发时 |

单元测试不能替代集成测试；测试替身通过不能证明真实外部依赖可用；全量测试通过
也不能替代质量评测、迁移演练、安全审查和人工验收。

## 3. 每次变更的最低要求

### 3.1 修改前

- 检查 Git 工作区和已有变更，避免覆盖用户工作。
- 识别本次修改影响的模块、公共契约、数据边界和外部依赖。
- 选择最小但足够的基线测试；已有明确失败时先记录，不盲目重跑。

### 3.2 修改后

默认执行：

1. 受影响单元测试。
2. 相关集成测试或契约测试。
3. 项目级 Ruff。
4. 受影响的类型检查；涉及共享接口或脚本入口时运行全项目 mypy。
5. 数据、迁移、安全和外部调用相关变更的专项验证。

以下情况可只运行定向验证，不运行全量测试：

- 仅修改文档、注释或测试数据，且不影响执行行为。
- 局部实现变化已由目标单元测试和相邻集成测试覆盖。
- 完成代码审查后的等价重构，已重跑受影响范围。
- 仅更新已经冻结的质量报告，且生成命令和输入未变化。

## 4. 全量测试触发条件

出现以下任一条件时，应运行全量 `pytest`，通常同时记录覆盖率：

1. 数据库 Schema、迁移、事务、级联删除或一致性规则变化。
2. 抓取、解析、切块、入库状态机、检索融合、证据构造等共享核心链路变化。
3. 公共 API 请求/响应契约或跨模块错误码变化。
4. 鉴权、安全边界、日志脱敏或密钥处理变化。
5. 依赖、锁文件、Python 版本、测试框架或 CI 配置变化。
6. 大型重构、跨多个模块的重构，或无法确定影响范围的变化。
7. 出现原因不明的跨模块回归。
8. 一个 BMAD 阶段完成、版本发布候选或迁移/回滚演练。
9. 用户明确要求全量验证。

不应仅因为“完成了一个模块”就自动运行全量测试。若模块改动局限在明确边界内，
定向测试足以证明影响范围时，应推迟到阶段验收再运行全量测试。

重复运行规则：

- 同一代码状态和同一失败条件不得重复运行同一命令。
- 修复失败后只重跑失败测试；影响共享代码时再扩大到相关测试集。
- 全量测试原则上每个验收门禁运行一次，不在中间小步重复执行。
- 用户要求停止测试后，立即停止正在运行或计划中的测试，并如实记录已完成的
  验证状态。

## 5. 模块、阶段与发布门禁

### 5.1 模块验收

- 目标模块单元测试通过。
- 相关集成/契约测试通过。
- Ruff 和适用类型检查通过。
- 验收标准有逐项证据。
- 不要求全量测试，除非命中第 4 节条件。

### 5.2 阶段验收

- BMAD 产物、实现、测试和人工确认一致。
- 相关模块验证全部通过。
- 默认运行一次全量 pytest 和覆盖率。
- 阶段级 E2E、质量评测、安全审查和故障演练按阶段要求执行。
- 未执行项、例外和残余风险必须记录。

### 5.3 发布候选

- 在同一提交上通过全量测试、Ruff、mypy 和覆盖率门禁。
- 主链路 E2E、冻结质量评测、迁移、备份和回滚验证有当前提交证据。
- 真实外部依赖检查只在授权、预算和安全条件满足时执行。
- 不得引用历史提交结果冒充当前版本验收。

## 6. 外部依赖与真实环境

默认测试必须离线、确定且不产生费用：

- Fetcher、Embedding、rerank 和 LLM 使用 Fake、Mock、本地夹具或冻结快照。
- 数据库使用临时 SQLite；不得读写用户真实知识库。
- CI 不依赖实时网页、外部 API Key 或个人机器状态。

真实依赖检查必须满足：

- 先说明目标、费用/配额、数据影响和失败恢复方式。
- 使用专用测试数据、测试 Key 或副本，不接触生产数据。
- 默认失败不修改外部状态；写入类操作必须获得明确授权。
- 报告命令、环境、参数、结果、时间和残余限制。
- 实时结果与冻结回归分开展示，不能把站点内容变化直接判定为代码缺陷。

冻结快照应记录来源 URL、抓取时间、最终 URL、HTTP 元数据、SHA-256 和人工标注。
真实页面快照用于回归，人工编写的边界夹具必须明确标记，不得冒充真实站点覆盖。

## 7. 测试数据与断言

- 优先复用仓库已有语料、夹具和测试辅助代码，避免无依据地建立第二套测试集。
- 新测试数据必须说明与项目定位、风险和验收目标的关系。
- 断言应验证可观察行为、边界、错误码和副作用，不能只检查对象非空或日志被调用。
- 禁止为了让测试通过而删除困难样本、修改生产默认值或降低已批准门槛。
- 解析、检索和模型质量指标必须记录语料版本、代码提交、模型和关键参数。

## 8. 失败、Flaky 与环境阻塞

1. 先读取失败断言、堆栈和输入差异，判断是本次回归、测试缺陷还是环境问题。
2. 修复本次引入的问题后，优先重跑失败测试。
3. 影响共享接口时扩大到相关测试集，不直接重复全量命令。
4. Flaky 测试最多重跑一次；仍不稳定时记录测试名、频率、环境和可能原因。
5. 环境或权限导致无法验证时，说明未执行项、替代证据和剩余风险，不得宣称通过。

## 9. 命令与 Token 控制

- 使用精确测试路径，避免无目的地运行整个 `tests/`。
- 默认使用安静输出和简短摘要；需要详情时只展开失败测试。
- 不在同一代码状态重复运行命令。
- 大范围测试输出只保留汇总、失败项和关键指标。
- 全量 pytest 与覆盖率只在第 4 节门禁执行。
- 文档修改不运行代码测试；仅需检查链接、Markdown、Git diff 和术语一致性。

## 10. 汇报格式

每次交付必须分别报告：

- **已通过**：实际运行的命令、范围和关键结果。
- **已执行但失败**：失败测试、现象和原因分析。
- **未执行**：未运行项目及原因，例如用户停止、成本限制或环境阻塞。
- **模块级验证**：单元、集成、静态检查。
- **阶段/发布级验证**：全量、覆盖率、E2E、质量、安全、迁移。
- **证据限制**：夹具与真实环境差距、历史结果、时间窗口和残余风险。

“相关测试通过”不得表述为“全量测试通过”；“模块完成”不得表述为“阶段完成”；
未运行项不得用计划、推断或历史结果代替。

## 11. Agent 执行清单

开始修改前：

- [ ] 已检查 Git 状态和现有变更。
- [ ] 已识别影响范围及需要执行的测试层级。
- [ ] 已确认是否需要真实外部依赖及授权。

修改完成后：

- [ ] 已运行受影响单元测试。
- [ ] 已运行相关集成/契约测试。
- [ ] 已运行 Ruff 和适用类型检查。
- [ ] 已判断是否触发全量测试，并记录原因。
- [ ] 已整理通过、失败、未执行和残余风险。

阶段或发布验收前：

- [ ] 已按门禁运行全量测试、覆盖率和专项验证。
- [ ] 已确认所有证据对应当前提交。
- [ ] 已回到 BMAD 判断下一项工作，不自行推进阶段。
